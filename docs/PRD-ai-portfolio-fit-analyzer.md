# PRD: AI Portfolio Fit Analyzer

## 1. Summary

Этот документ описывает MVP веб-приложения, которое оценивает, насколько портфолио кандидата подходит под конкретную вакансию. Продукт должен выглядеть как нормальный полезный сервис, но при этом работать как сильный demo-проект для отклика на вакансию “вайбкодера”: быстро собранный, ясный, визуально аккуратный и с явным стеком `Next.js + React + Supabase + Vercel`.

Главная идея: пользователь создает вакансию, получает AI-анализ требований и критериев, добавляет кандидатов со ссылками на GitHub и сопроводительным письмом, а затем получает структурированные отчеты и финальный выбор лучшего кандидата.

Ключевой принцип продукта: сервис не оценивает кандидатов по заранее зашитому стеку. Он каждый раз строит оценку на основе критериев, извлеченных из конкретной вакансии.

## 3. Background

### Контекст

У автора уже есть два сильных проекта с явным backend-уклоном:

- `call_reviewer`
- `transcriber`

Этого достаточно, чтобы показать работу с API, пайплайнами и серверной логикой. Но для отклика на вакансию “вайбкодера” не хватает другого сигнала:

- умение быстро собирать продуктовый интерфейс;
- уверенная работа с `Next.js` и `React`;
- использование `Supabase Cloud` как практичной backend-платформы;
- понимание UX, при котором продукт выглядит собранным, а не просто “технически существующим”.

### Почему сейчас

Нужен проект, который можно сделать за часы или дни, быстро задеплоить на `Vercel` и сразу показывать как убедимый артефакт. Он должен считываться как продукт, а не как набор экранов.

### Почему эта идея подходит

Сервис оценки кандидатов по вакансии одновременно:

- выглядит полезным и понятным;
- дает пространство для AI-функций;
- показывает продуктовый вкус;
- сохраняет пост-ироничную идею, не превращаясь в шутку ради шутки.

### Почему это стало возможным

Сейчас такой MVP реально собрать быстро, потому что есть:

- зрелый стек `Next.js + React + shadcn/ui`;
- `Supabase` для аутентификации и хранения данных;
- AI-модели для извлечения критериев и оценки кандидатов;
- простой деплой на `Vercel` без сложной инфраструктуры.

## 4. Objective

### Цель

Собрать MVP веб-приложения, которое помогает сравнивать кандидатов с вакансиями по GitHub-портфолио и сопроводительным материалам, а также показывает умение быстро делать законченные AI-first прототипы.

### Почему это важно

Для пользователя продукт решает понятную задачу: помогает быстро понять, кто лучше подходит под вакансию и что именно стоит улучшить кандидату.

Для автора проекта продукт решает демонстрационную задачу:

- показывает владение `Next.js`, `React`, `Supabase`, `shadcn/ui`;
- демонстрирует скорость сборки продукта;
- показывает не только код, но и мышление про интерфейс, сценарии и полезность.

### Связь со стратегией

Этот проект дополняет уже существующие backend-репозитории и закрывает недостающий сигнал: “я умею не только строить серверную логику, но и быстро собирать нормальный продуктовый веб-сервис”.

### Key Results

**Objective:** Запустить за короткий срок рабочий MVP, который можно показать как портфолио-проект для отклика.

**KR1:** Пользователь может зарегистрироваться, создать вакансию, добавить минимум 3 кандидатов и получить сравнимые отчеты без ручной работы с базой данных.

**KR2:** Все вакансии, кандидаты и отчеты сохраняются в `Supabase` и доступны после перезагрузки страницы и повторного входа.

**KR3:** Приложение деплоится на `Vercel` через переменные окружения без отдельной серверной инфраструктуры.

**KR4:** Основной сценарий “вакансия -> критерии -> кандидаты -> выбрать лучшего” проходит в интерфейсе за 5-10 минут и выглядит цельно.

## 5. Market Segment(s)

### Сегмент 1. Кандидат, который адаптирует портфолио под вакансию

**Работа, которую нужно сделать:** понять, насколько его GitHub и портфолио подходят под конкретную роль, и что стоит усилить в отклике или на интервью.

**Проблема:** сложно честно оценить себя по тексту вакансии, особенно когда требований много и они размыты.

### Сегмент 2. Нанимающий менеджер или техлид

**Работа, которую нужно сделать:** быстро сравнить нескольких кандидатов по единой системе критериев, не собирая заметки вручную.

**Проблема:** у кандидатов разные форматы портфолио, разный уровень описания проектов и разные сильные стороны. Сравнение получается шумным.

### Сегмент 3. Рекрутер или фаундер маленькой команды

**Работа, которую нужно сделать:** принять быстрое предварительное решение по короткому списку кандидатов.

**Проблема:** нет времени на глубокий ручной разбор каждого GitHub-профиля и сопроводительного письма.

### Ограничения сегментов для MVP

- Работаем с небольшим числом кандидатов на одну вакансию.
- Источник сигнала ограничен текстом вакансии, ссылками и сопроводительным письмом.
- Нет ATS-интеграций, командной работы и сложных ролей доступа.

## 6. Value Proposition(s)

### Основное обещание продукта

“Загрузи вакансию, добавь кандидатов и быстро получи понятный отчет: кто подходит лучше, почему и что стоит улучшить”.

### Ценность для пользователя

- Не нужно вручную выписывать требования из вакансии.
- Не нужно держать сравнение кандидатов в голове или в таблице.
- Можно вернуться к старым отчетам, потому что они сохраняются.
- Оценка не ограничивается одним числом: сервис показывает сильные стороны, пробелы и практические рекомендации.

### Боли, которые продукт снимает

- Размытые критерии оценки.
- Субъективное сравнение кандидатов.
- Потеря контекста между сессиями.
- Слабая подготовка к отклику или интервью.

### Что пользователь получает

- Общую оценку соответствия вакансии.
- Структурированный разбор по критериям.
- Сильные стороны кандидата.
- Пробелы и слабые места.
- Практические рекомендации: что подтянуть, что подчеркнуть в отклике, что проговорить на интервью.

### Почему продукт лучше типового “резюме-сканера”

- Он оценивает не только текст резюме, но и портфолио через ссылки.
- Он работает вокруг вакансии и ее критериев, а не вокруг абстрактной “общей пригодности”.
- Он позволяет сравнить нескольких кандидатов внутри одной вакансии.
- Он выглядит как маленький продукт, а не как одноразовая утилита.

## 7. Solution

### 7.1 UX / Prototypes

#### Общий принцип UX

Интерфейс должен быть простым, собранным и быстрым. Основной экран строится вокруг двухпанельной структуры:

- слева список вакансий и кнопка `Создать вакансию`;
- справа подробности выбранной вакансии, критерии оценки и список кандидатов.

#### Основные экраны

**1. Экран логина**

- email / логин;
- пароль;
- кнопка входа;
- ссылка на регистрацию;
- без соцсетей и лишних вариантов.

**2. Главный экран**

- левая колонка с вакансиями;
- правая рабочая зона на 70-80% ширины;
- блок текста вакансии;
- блок критериев;
- блок кандидатов;
- основная CTA-кнопка для финального выбора кандидата.

**3. Мастер создания вакансии**

Шаги:

1. Ввести название вакансии и текст вакансии.
2. Показать экран AI-анализа с прогрессом.
3. Показать критерии для inline-редактирования.
4. Сохранить вакансию и вернуться в рабочий экран.

**4. Форма создания кандидата**

- имя кандидата;
- GitHub URL;
- дополнительные ссылки;
- сопроводительное письмо текстом или файлом;
- кнопка запуска анализа.

**5. Экран отчета по кандидату**

- общий score;
- разбор по критериям;
- сильные стороны;
- слабые стороны;
- рекомендации.

**6. Финальный экран выбора лучшего кандидата**

- сравнение всех кандидатов по общей оценке;
- объяснение, почему выбран победитель;
- краткий финальный вывод.

#### Базовые shadcn-блоки для реализации

Для ускорения сборки MVP и сохранения консистентного UI в проекте фиксируются следующие стартовые блоки:

- экран входа собирать на основе `login-01`;
- основное рабочее окно собирать на основе `sidebar-02`.

Команды:

```bash
npx shadcn@latest add login-01
npx shadcn@latest add sidebar-02
```

Это решение нужно понимать как обязательную базу для MVP, а не как рекомендацию.

#### Основные пользовательские потоки

**Поток вакансии**

`Создать -> Анализ -> Отредактировать критерии -> Сохранить`

**Поток кандидата**

`Создать -> Анализ -> Получить отчет`

**Поток завершения подбора**

`Открыть вакансию -> Нажать "Выбрать лучшего кандидата" -> Получить итоговое решение`

#### UX-акценты

- Минимум пустых состояний: каждый экран должен вести к следующему действию.
- Хорошие loading-состояния во время AI-анализа.
- Inline-редактирование критериев вместо сложного отдельного редактора.
- Отчеты читаются как продуктовый артефакт, а не как сырые JSON-поля.

### 7.2 Key Features

#### F1. Аутентификация

- Регистрация и вход по email/паролю.
- Сессии через `Supabase Auth`.
- Доступ к данным только текущего пользователя.

#### F2. Список вакансий

- Просмотр всех вакансий пользователя.
- Выбор активной вакансии в левой панели.
- Создание новой вакансии из главного экрана.

#### F3. Создание вакансии

- Поля: название и текст вакансии.
- AI-анализ текста вакансии.
- Автоматическое извлечение:
  - требований;
  - критериев оценки;
  - опционально весов критериев.
- Экран редактирования критериев перед сохранением.

#### F4. Хранение вакансии

- Сохранение текста вакансии.
- Сохранение итогового набора критериев.
- Привязка вакансии к конкретному пользователю.

#### F5. Создание кандидата

- Имя кандидата.
- Ссылки на GitHub и портфолио.
- Сопроводительное письмо:
  - как текст;
  - или как файл.
- Привязка кандидата к выбранной вакансии.

#### F6. Анализ кандидата

- AI-сопоставление кандидата с критериями конкретной вакансии.
- Оценка строится по signals из GitHub, портфолио и сопроводительного письма, а не по фиксированному стеку продукта.
- Генерация структурированного отчета.
- Сохранение итогового score и текстового разбора.

#### F7. Просмотр кандидатов

- Список кандидатов внутри вакансии.
- Выбор кандидата из списка.
- Показ детального отчета справа.

#### F8. Финальное решение

- Кнопка `Выбрать лучшего кандидата`.
- Повторный анализ всех кандидатов внутри вакансии.
- Выбор лучшего кандидата на основе сохраненных критериев и отчетов.
- Отображение короткого объяснения решения.

#### F9. История и возврат

- Все данные хранятся в `Supabase`.
- Пользователь может вернуться к вакансии и старым отчетам позже.

#### Подход к архитектуре

- Фокус на thin backend и хорошем frontend UX.
- Серверная логика остается минимальной: только то, что нужно для auth, хранения данных и AI-вызовов.
- Аналитика вакансии и кандидата запускается из серверных action/route handler-ов.
- Нет отдельного сложного worker-слоя в MVP.

#### Vacancy-driven repo evaluation pipeline

Главный технический принцип: scoring engine не должен быть привязан к одному стеку или типу вакансии.

- Нельзя хардкодить в ядро оценки конкретные технологии вроде `Next.js`, `React`, `Supabase` как универсальную норму.
- Можно хардкодить только категории сигналов и общую механику оценки.
- Конкретные технологии, требования и веса должны появляться из текста вакансии и сохраняться как данные.

Пайплайн MVP:

1. Пользователь создает вакансию и вставляет текст описания.
2. AI извлекает требования и критерии оценки.
3. Каждый критерий сохраняется с полями `title`, `description`, `weight`, `kind`, `evidence_rules`.
4. Пользователь добавляет GitHub-ссылку кандидата.
5. Сервис нормализует ссылку:
   - если это репозиторий, анализирует его;
   - если это профиль, выбирает ограниченный набор релевантных репозиториев.
6. Через GitHub API и доступные публичные артефакты сервис собирает `repo digest`, а не полный дамп репозитория.
7. Scoring engine сопоставляет `repo digest` с критериями текущей вакансии.
8. LLM получает вакансию, критерии, `repo digest` и сопроводительный контекст, после чего пишет отчет и объясняет score.

Что извлекать из репозитория или профиля:

- stack signals: языки, фреймворки, библиотеки, базы данных, облачные сервисы;
- architecture signals: API, auth, storage, background jobs, migrations, integrations, monorepo;
- quality signals: тесты, CI, lint, typing, docs, env example, понятная структура;
- product signals: UI, forms, dashboards, onboarding, CRUD, роли, состояния интерфейса;
- delivery signals: deploy-конфиги, `Vercel`, `Docker`, release hygiene;
- activity signals: свежесть коммитов, частота изменений, признаки завершенности;
- domain signals: аналитика, ML, fintech, e-commerce и другие предметные области.

Правила scoring:

- Каждый критерий оценивается по шкале `0..5`.
- У каждого критерия есть вес.
- У каждого балла должен быть `evidence`.
- Если данных недостаточно, система должна возвращать `unknown`, а не придумывать отрицательную оценку.
- Итоговый score считается только по критериям текущей вакансии.

Ограничения MVP:

- Не клонировать репозиторий.
- Не запускать пользовательский код.
- Не строить тяжелый ingestion pipeline.
- Не индексировать весь репозиторий целиком, если можно обойтись digest-представлением.

#### Интеграция с AI

В MVP AI-провайдер не является главной частью продукта и может быть заменяемым. Важно не “показать сложную ML-систему”, а быстро дать пользователю полезный результат.

Требование к провайдеру:

- AI-провайдер должен быть `OpenAI API compatible`.
- Интеграция не должна быть жестко привязана к одному вендору.
- Смена провайдера должна делаться через конфиг, без переписывания продуктовой логики.

Обязательные параметры конфига:

- `LLM_BASE_URL`
- `LLM_API_KEY`
- `LLM_MODEL`

Назначение параметров:

- `LLM_BASE_URL` задает базовый URL OpenAI-compatible API;
- `LLM_API_KEY` задает ключ доступа;
- `LLM_MODEL` задает модель, которая используется для анализа вакансий, кандидатов и финального decision flow.

Следствие для архитектуры:

- клиент для LLM должен создаваться через единый конфиг-слой;
- продуктовый код не должен зависеть от конкретного названия провайдера;
- в `Vercel` и локально используется один и тот же набор переменных окружения.

#### Требования к деплою

- Один проект на `Vercel`.
- Секреты через `.env.local` и переменные окружения `Vercel`.
- LLM-конфиг также передается через переменные окружения:
  - `LLM_BASE_URL`
  - `LLM_API_KEY`
  - `LLM_MODEL`
- `Supabase Cloud` как внешняя managed-платформа.

### 7.4 Assumptions

- Для MVP достаточно `email + password` без OAuth.
- Для первой версии достаточно одного рабочего пространства на пользователя.
- Ссылок на GitHub и текстового контекста хватит, чтобы сгенерировать убедительный demo-отчет.
- Анализ вакансии должен быть редактируемым, потому что AI может ошибаться.
- Время ожидания анализа должно быть небольшим; если оно выше, интерфейс обязан компенсировать это хорошими loading-состояниями.
- Главная ценность MVP не в абсолютной точности оценки, а в качестве прототипа, ясности UX и убедительности сценария.

## 8. Release

### Что входит в первую версию

**V1 / MVP**

- Аутентификация по email и паролю.
- Главный экран с двумя панелями.
- Создание вакансии через 4-шаговый flow.
- AI-анализ вакансии и редактирование критериев.
- Создание кандидата с GitHub-ссылкой и сопроводительным письмом.
- Генерация и сохранение отчета кандидата.
- Просмотр кандидатов внутри вакансии.
- Финальная кнопка выбора лучшего кандидата.
- Хранение данных в `Supabase`.
- Деплой на `Vercel`.

### Что можно оставить на fast follow

- Парсинг GitHub API с дополнительными метриками.
- Извлечение текста из загруженных файлов.
- Экспорт отчетов в PDF.
- Публичная ссылка на вакансию или отчет.
- Комментарии и совместная работа.
- Более умные весовые модели и тонкая настройка критериев.

### Рекомендуемый темп реализации

**Этап 1. Базовый каркас**

- инициализация `Next.js`;
- подключение `shadcn/ui`;
- настройка `Supabase Auth`;
- базовый layout и пустые состояния.

**Этап 2. Вакансии**

- список вакансий;
- мастер создания вакансии;
- сохранение критериев.

**Этап 3. Кандидаты и отчеты**

- форма кандидата;
- анализ;
- просмотр отчетов;
- сохранение данных.

**Этап 4. Финальная полировка**

- выбор лучшего кандидата;
- loading и skeleton-состояния;
- визуальная полировка;
- деплой на `Vercel`.

### Definition of Done для MVP

- Приложение локально запускается без ручных обходных путей.
- Пользователь может пройти сквозной сценарий от регистрации до финального выбора кандидата.
- После обновления страницы данные не теряются.
- Интерфейс выглядит как законченный продуктовый прототип, а не как технический черновик.
- Репозиторий и деплой явно показывают стек `Next.js + React + Supabase + Vercel`.
